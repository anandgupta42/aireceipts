# Aireceipts: The Deterministic FinOps Layer for Coding Agents

## Executive Summary

- **Make Cache Waste Visible**: Anthropic documents 5-minute cache writes at 1.25x input price, 1-hour writes at 2x, and cache reads at 0.1x, while batch cache-hit rates can vary from 30% to 98% with traffic patterns [17] [14]. Aireceipts should report observed cache reuse, write premiums, TTL, and invalidation events before recommending prompt changes.
- **Turn Context Into a Ledger**: Every system prompt, message, tool definition, tool result, image, document, and generated output counts toward context, and Claude Code says stale context wastes tokens on subsequent turns [27] [6]. Add a per-turn context bill of materials, including CLAUDE.md, MCP schemas, compactions, and oversized results.
- **Report Routing, Do Not Pretend to Rank Models**: Current Claude documentation lists materially different input/output prices and context windows across Fable, Opus, Sonnet, and Haiku [16]. Aireceipts can calculate a cheaper-model or lower-effort counterfactual, but it cannot infer whether quality would survive without an evaluation outcome.
- **Detect Waste Before It Becomes a Failure**: In a 1,794-trajectory CLI-agent sample, repeating the same approach appeared in 15% of failed trajectories and accounted for 29% of wasted execution; repairing the wrong problem appeared in 24% and accounted for 39% [2]. Add deterministic loop, no-progress, and recovery-window alarms.
- **Use Tests and Git as Ground Truth**: In 33,596 agentic pull requests, 71.48% merged, 17% of annotated rejections were CI or test failures, and each additional failed CI check reduced merge odds by approximately 15% [11] [11] [11]. Attach cost to test outcomes and gate CI on marginal agent spend, not on a model judgment.
- **Give Managers Unit Economics**: FinOps guidance calls for cost per query, user, workflow, and business transaction because raw tokens and dollars do not connect spend to outcomes [28]. Add cost per merged PR, surviving accepted line, successful task, repository, developer, and failure-recovery episode.
- **Reconcile With Existing Telemetry**: Claude Code exposes cost, token, session, edit-decision, active-time, line-count, commit, and pull-request metrics through OpenTelemetry [4] [4] [4]. Aireceipts should ingest or export these fields so a local receipt can become an organization-level showback record.
- **Treat Published Spend as a Distribution Signal**: Claude Code documentation reports about $13 per developer per active day and $150-250 per developer per month, with 90% of users below $30 per active day; OpenAI reports Codex at approximately $100-200 per developer per month [6] [1]. These are not comparable invoices, so the product should show distributions, billing basis, and plan-equivalent counterfactuals rather than declare a winner.

## 1. Cost-Optimization Levers and Deterministic Recommendations

Aireceipts already has the right premise: compute from observed transcripts and cited price tables, not from a model's opinion. The next step is to expose the hidden multipliers that make two sessions with the same final patch have very different costs. The table below separates published evidence, expected value, and a computation that requires no model call.

| Lever | Evidence | Expected savings or value | What aireceipts can compute or recommend deterministically |
|---|---|---|---|

Label the ratio as observed cache-accounted reuse when the provider does not expose the full cache key. |

Claude Code recommends Sonnet for most coding, Opus for complex architecture, and Haiku for simple subagents [6]. | A lower tier can reduce list-price spend, particularly when output or thinking tokens dominate. ### Cache economics should become a first-class receipt

The simple break-even math is useful and safe. Let `h` be the fraction of cache-accounted prefix tokens read from cache. Ignoring provider exceptions, a 5-minute cache has an average input-price multiplier of `(1-h)*1.25 + h*0.10`. It beats uncached input when `h` is above approximately **21.7%**. A 1-hour cache has `(1-h)*2.00 + h*0.10` and breaks even above approximately **52.6%**. These are arithmetic implications of the published multipliers, not promises about an application. A receipt should show the assumptions beside the result.

Anthropic says cache lifetimes are measured from the start of the request that writes or reads the entry, and permits up to four cache breakpoints [17] [17]. It also says that batch cache hits are best effort and traffic-dependent, with typical reported rates from 30% to 98% [14]. Aireceipts should therefore distinguish four metrics: cache-read tokens, cache-creation tokens, uncached input tokens, and a provider-reported or locally observed hit ratio. It should not call `cache_read / (cache_read + cache_creation)` a universal hit rate when the transcript omits the full eligible prefix.

Claude Code's own telemetry makes this feasible. The token event has `input`, `output`, `cacheRead`, and `cacheCreation` types, while request attributes include input tokens, output tokens, cache-read tokens, cache-creation tokens, cost, model, effort, speed, query source, request ID, and tool or MCP names [4] [4]. The product can turn those fields into a cache waterfall: first write, reuse, expiry, invalidation, and residual input. That is more actionable than a single weekly dollar total.

### Case study: Claude Code exposes the cost surface aireceipts should normalize

Claude Code's documentation connects model choice, context size, thinking, subagents, and per-developer cost in one operational surface. It says enterprise deployments average around $13 per active developer-day and $150-250 per developer-month, while 90% of users remain below $30 per active day [6]. It also says displayed costs use list prices by default and may not match contracted billing [6].

The product implication is not to copy Claude Code's ranking of models. It is to preserve the causal chain in a portable receipt: a tool result added tokens, the next request paid for those tokens, a changed tool schema destroyed a prefix cache, a high-effort call added reasoning output, and a retry followed a failed test. This is exactly the kind of attribution that remains deterministic across providers.

## 2. Failure Modes and Waste Patterns Detectable From Transcripts

Aireceipts should treat a failure label as a deterministic observation, not a diagnosis of a model's internal state. The strongest signals are repeated commands, unchanged files, exit codes, tool rejection results, timestamps, token counts, and Git or CI outcomes. When the evidence supports only a symptom, use a neutral label such as `repeated-test-without-change` rather than `bad reasoning`.

| Pattern | Published evidence | Deterministic detector | Expected value |
|---|---|---|---|
| Retry storm or infinite agentic loop | Infinite Agentic Loops are defined as unbounded repeated model calls, tool calls, workflow transitions, or handoffs. A scan of 6,549 repositories found 74 potential findings and manual review confirmed 68 failures across 47 projects with 91.9% precision [21] [21]. | Detect the same request, tool call, parser error, or state hash repeated without a new file or environment change. Apply hard limits on turns, wall time, retries, and dollars. | Stop or flag cost exhaustion. Compute cost after the first repeated state and the counterfactual if execution had stopped at the configured bound. |
| Edit-fail loop | In the CLI trajectory study, repeating the same approach occurred in 15% of failed trajectories and contributed 29% of wasted execution; repairing the wrong problem occurred in 24% and contributed 39% [2]. | Track edit or write attempts by path, patch hash, result status, and subsequent test result. Flag repeated rejected edits, identical patches, or edits to a file whose failure signal did not change. Claude Code telemetry includes edit decisions and tool names [4]. | Show cost and time after first rejected edit, and recommend a human stop, a fresh diagnosis, or a test before another edit. |
| Repeated file reads | The trajectory study finds repetitive, non-adaptive cycles and says action repetition is several times higher in failing trajectories [8] [8]. | Hash path, byte range, and returned content. Flag rereads with no intervening write, test, or relevant error, and distinguish cheap metadata reads from large source or log reads. | Quantify input tokens, time, and cache impact attributable to redundant reads. Recommend a narrower range, a summary command, or a subagent only when the repeated payload is large. |
| Test-suite reruns and redundant verification | A 4,644-run study found that the highest observed redundant-verification level cost 18.25x the clean-run median, used 15 rather than 6 median tool calls, and took 3x the wall clock with no success gradient [25] [25]. | Normalize command, working tree hash, relevant file hashes, exit code, and failure output. Flag an unchanged test rerun, post-success verification with no state change, and a full suite rerun after a narrowly scoped edit. | Report the marginal dollars and minutes, not merely the count. A repository policy can permit one confirmation run and require an explicit reason for more. |
| Giant outputs and context bloat | Tool results re-enter context, add input tokens, alter cache accounting, and can induce more turns [25]. Tool definitions and tool results both count toward the context window [27]. | Count output bytes and tokens, largest lines, repeated blocks, log-to-useful-content ratio, and the fraction of the next context occupied by each result. | Recommend bounded output, filtering, pagination, `head` or `tail`, structured JSON, or subagent isolation. State the exact tokens and future-turn cost exposed by the receipt. |
| Checks that cannot change the outcome | In the process study, checks that could not change the outcome appeared in 28% of failed trajectories and accounted for 15% of wasted execution [2]. | Compare a check's inputs and repository state with the prior check. If neither can change, flag a redundant check. | Give a conservative waste line and avoid claiming the check was useless unless the state identity proves it. |
| Hallucinated or misused APIs | In an API-evolution benchmark across eight Python libraries, adoption failures included omission at 42.1%, old API usage at 16.4%, and execution failures included incorrect parameters at 26.6% and hallucinated behavior at 16% [23]. The benchmark covers 270 API updates and four model families, so these are benchmark-specific, not universal coding-agent prevalence [23]. | Without a model, detect import-not-found, attribute-not-found, undefined symbol, invalid parameter, 404, compiler, type-checker, and test failures. Match the error to a preceding new API call or symbol. Label `API-use failure evidence`, not hallucination, unless a local package or documentation check proves nonexistence. | Charge the failed call and all retries, show the first deterministic error, and recommend a local API or type check before another generation. |
| Runaway or abandoned session | Failed CLI trajectories had a decisive error around step 7 and a median length of 27 steps; 15% kept repeating the same approach [2] [2]. | Flag cost or time continuing after the last file change, after a terminal error, or after a successful test. Track no-progress intervals, concurrent sessions, and spend velocity. | Provide a burn-rate alarm and a stop threshold. Do not infer that a long session is waste if it is making verified progress. |
| Fabricated success or stale final report | Fabricated success appeared in 26% of failed trajectories in one study, and 84% of those cases began at or after lock-in [2]. In a separate taxonomy, inaccurate self-reporting accounted for 22.58% of episodes [26]. | Compare final textual status patterns with last test exit code, CI status, Git diff, commit, and pull-request state. If the transcript contains no final claim, report only the objective state. | Prevent false green receipts and identify the exact failed command that should block merge. This is a consistency check, not a semantic model call. |

### Case study: empirical failure rates point to process controls, not model rankings

The largest process study here collected 3,843 executions from seven models across three agent scaffolds, retained 1,794 valid trajectories, and analyzed more than 63,000 execution steps [2] [2] [2]. Its useful result for aireceipts is temporal: the decisive error often happens early, but a failed run can continue for many steps. The recovery window has a median of one step, while 60.9% of decisive errors still leave at least one recovery step [2].

That finding supports a deterministic intervention: report the first error, the remaining recoverable window, and the cost incurred after it. Do not merely mark the final task as failed. The same study found that 15% of failures repeated the same approach, 24% repaired the wrong problem, and 28% performed checks that could not change the outcome [2]. A receipt can expose all three patterns from action and state history without judging code quality.

The agentic-PR study provides a second ground truth. It analyzed 33,596 pull requests from five agents, with 24,014 merged, and manually classified 600 rejected PRs [11] [11] [11]. Rejected PRs were larger and had more CI failures; each additional failed check reduced merge odds by approximately 15% [11]. This makes test rerun cost and CI failure cost directly relevant to a PR receipt.

## 3. Engineering-Manager Metrics, Unit Economics, and Observability

The manager-facing product should not stop at total spend. It should connect dollars to a workflow outcome while preserving the distinction between observed fact, derived metric, and proxy. FinOps guidance explicitly recommends cost per query, cost per user, cost per workflow, and cost per business transaction, and warns that raw tokens and dollars are insufficient [28].

| Metric | Definition for aireceipts | Value and decision | Deterministic data required |
|---|---|---|---|
| Cost per merged PR | Attributable agent cost for the branch, session, or PR divided by merged PRs in the period. Also show cost per PR that remains un-reverted for a configured window. | Measures delivered output rather than generated code. Keep merged and unmerged denominators separate. | Session IDs, Git branch, commit, PR number, model price, token usage, CI state, merge state, and optional revert state. |
| Cost per accepted line | Cost divided by added lines that survive the merge or review policy. Report raw added, removed, net, and surviving lines separately. | Useful as a rough production-throughput metric, but LOC is not quality. Pair it with tests, rework, and review outcomes. | Git diffs, merge commit, later reverts, and Claude Code line-count metrics. Claude Code exposes added and removed line types and model attributes [4]. |
| Cost per successful task | Cost divided by tasks whose configured test or CI predicate passes. | Avoids rewarding cheap but failed attempts. | Task ID, final test status, cost, retries, and explicit success predicate. |
| Cost concentration | Share of spend by developer, repository, model, provider, tool, and automation, including top 1%, 10%, and 25% users. | Finds power users, runaway repos, and a small number of expensive models that dominate budget. | User or workspace identity, repository, model, session, and cost. |
| Burn rate | Spend per active day and trailing 7, 30, and 90 days, plus a run-rate forecast using only observed spend. | Makes a spike visible before the monthly invoice. Do not forecast beyond a stated window or claim certainty. | Timestamp, cost, active-day definition, and user or repository. |
| Per-repository budget | A versioned dollar, token, or active-day budget attached to a repository. | Enables local showback and a deterministic warning or CI failure before an approved limit is exceeded. | Repository identity, receipt total, budget file, and exit status. |
| CI cost gate | Fail or warn when a PR exceeds a configured marginal cost, repeats a test without a state change, or increases failure-recovery cost. | Converts a receipt into a policy control while keeping the rule auditable. | CI environment, PR, diff hash, test command, prior receipt, and threshold. |
| Cache and context efficiency | Cache reuse, cache-creation share, uncached input, context growth, compaction frequency, and tool-result share. | Identifies recurring tax before selecting a cheaper model. | Provider usage fields, token counts, visible prompt structure, and compaction events. |
| Time to verified result | Wall time and active model time from first prompt to passing test or merge. | Prevents an apparent dollar saving from creating a slower, less reliable workflow. | Timestamps, tool durations, test status, and merge state. |

### What comparable systems already surface

Claude Code's OpenTelemetry surface includes `claude_code.session.count`, `claude_code.token.usage`, `claude_code.code_edit_tool.decision`, `claude_code.active_time.total`, `claude_code.lines_of_code.count`, `claude_code.commit.count`, `claude_code.pull_request.count`, and `claude_code.cost.usage` [4] [4] [4]. Its attributes include model, token type, query source, speed, effort, agent, skill, plugin, MCP server, and MCP tool [4]. Request-level attributes include cost, duration, token breakdown, request IDs, and correlation IDs [4] [4]. This is a strong interoperability target for aireceipts.

Grafana's coding-agent dashboards illustrate the manager questions: cost, token consumption, sessions, model usage, tool invocations, latency, and errors [15]. Its provider views include Claude Code cost, sessions, prompts, API requests and errors, daily cost and token trends, model breakdown, and tool analytics [15]. Langfuse tracks usage and cost across models, use cases, and time, supports dashboards by model, tags, or users, threshold alerts, and a Metrics API for filtering by application, user, or tags [10].

Aireceipts should not try to become a hosted tracing platform. Its differentiation is local, deterministic attribution from raw transcripts, Git, and optional OTel records. The useful bridge is an exportable receipt schema with stable fields for `session_id`, `request_id`, `tool_use_id`, `repo`, `pr`, `model`, `effort`, `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_creation_tokens`, `cost_usd`, `duration_ms`, `failure_signature`, and `policy_result`.

### Case study: FinOps and observability show why PR economics belongs beside tokens

FinOps guidance says provider invoices normally show spend by API key or project rather than by business unit, cost center, application, or team, and recommends deliberate instrumentation plus shared dashboards for showback and chargeback [28] [28]. That is precisely the gap a local receipt can close for a repository owner: the transcript knows which branch and tool produced the tokens, while Git and CI know whether the work merged.

The observable fields already support a practical minimum. Claude Code can expose cost, token type, model, active time, edit decisions, lines, commits, and pull requests [4] [4] [4]. The next product layer is not another token chart. It is a join that says, for example, which repository consumed the most output tokens per merged PR, which tool generated the largest rejected-edit cost, and which model tier dominated failed recovery.

The published numbers are useful as planning anchors, not as a benchmark of equivalent products.

Included plan limits are used first for standard Business seats, while purchased credits can support continued usage; Codex-only seats require workspace credits from first use [1]. This is why a monthly receipt needs a `billing_basis` field such as `api_list`, `contracted_api`, `subscription_allowance`, `workspace_credits`, or `unknown`.

### Case study: subscription versus usage-based billing

A heavy, predictable developer may find an allowance-based plan attractive, while a light or automated user may benefit from pay-as-you-go controls. That conclusion cannot be derived from transcript dollars alone because the transcript does not know the user's plan, shared allowance, tax, contract, or whether a credit draw came from a pooled workspace.

Aireceipts can still make the decision transparent. It can calculate list-price-equivalent spend from the observed token mix, add a user-entered monthly plan price, show allowance consumed, and calculate the utilization at which the plan would break even. For Codex it can also show the actual credit rate by model, concurrent instance count, automation count, and Fast-mode use, because the rate card identifies those as cost drivers [1].

The recommendation should be phrased as: "At the entered price and allowance, this observed workload would have cost X on API list pricing and Y against the subscription allowance. Contract, quality, latency, and remaining quota are not observed." That is useful arbitrage analysis without pretending that a subscription dollar is the same unit as an API invoice.

## Synthesis: What Aireceipts Can Know and What It Must Not Infer

The roadmap should prioritize controls with high observability and clear intervention points. Three strategy families have different scopes and confidence levels.

| Strategy family | Mechanism | Scope | Trade-off | Evidence and confidence |
|---|---|---|---|---|
| Cache and context hygiene | Keep stable prefixes, avoid oversized results, isolate verbose work, and reduce repeated input. | Every turn after the waste begins. | A smaller context or shorter TTL can lose useful information or reduce cache reuse. | High for token and cost attribution when usage fields exist; medium for hidden MCP or provider cache state. |
| Model and effort routing | Use a lower-priced model, lower effort, or batch tier for a workload that meets an explicit policy. | Per request, task class, or automation. | Lower nominal price can create more retries, rework, or latency. | High for arithmetic counterfactual; low for quality unless Git, tests, review, and merge outcomes are linked. |
| Workflow guardrails and unit economics | Stop loops, cap retries, gate CI, and allocate cost to repositories and PRs. | Session, PR, repository, and organization. | A strict cap can stop a recoverable run; a PR metric can reward low-quality small changes. | High for observable states and outcomes; medium for causal attribution of business value. |

The non-obvious tension is that the cheapest visible request can be the most expensive workflow. A cheaper model that fails a test and then retries four times can lose to a more expensive first pass. A 50% Batch discount can be offset by poor cache reuse or an unacceptable 24-hour wait. A compaction may reduce context pressure but force the agent to reread files. A subscription may hide marginal spend while a shared allowance becomes the scarce resource.

The product should therefore report two layers. The first is fact: tokens, price row, cache fields, tool calls, files, exit codes, tests, commits, PR state, and time. The second is a clearly labeled recommendation: stop, clear, isolate, route, batch, lower effort, cap, or budget. It must never claim that a model is better, that a hallucination occurred, or that a subscription is cheaper unless the relevant evidence and user-supplied billing assumptions exist.

The hard boundary is hidden computation. Claude's prompt cache can be partially opaque, and OpenAI reasoning tokens are not visible in the API even though their aggregate count is reported in usage [18]. A transcript reader can account for reported tokens and visible state transitions; it cannot reconstruct unreported internal thought, a provider's hidden cache key, or quality that no outcome record measures. That limitation is a product strength if the receipt states it explicitly.

## Prioritized 20-Feature Roadmap

1. **P0: Versioned provider price-table registry.** Store model, input, output, cached-input, cache-write, long-context, Batch, Flex, Fast, and subscription assumptions with source URL, retrieval date, and citation. This prevents fabricated dollars and lets every recommendation be reproduced.
2. **P0: Cache economics ledger.** Parse `cacheRead` and `cacheCreation` token types, TTL where available, writes, reads, uncached input, and observed reuse. Show the 5-minute and 1-hour break-even calculation using the published 1.25x, 2x, and 0.1x multipliers [17].
3. **P0: Cache invalidation fingerprint report.** Hash visible tool definitions, system blocks, message prefixes, search and citation toggles, speed, and tool choice. Attribute the next miss to the first changed layer and mark hidden causes unknown.
4. **P0: Per-turn context bill of materials.** Attribute tokens and cost to system instructions, CLAUDE.md, messages, tool schemas, tool results, thinking, and output. This operationalizes the fact that all of these components consume context [27].
5. **P0: Instruction and MCP overhead linter.** Count CLAUDE.md lines and tokens, flag the documented 200-line guidance threshold, list unused MCP schemas, and report schema bytes without judging their semantic usefulness [6] [6].
6. **P0: Compaction, restart, and isolation tax report.** Measure compaction count, before and after context, summary tokens, rereads after compaction, subagent cost, and team-member cost. Include the observed team multiplier rather than assuming a fixed one [6] [6].
7. **P0: Oversized-result detector.** Rank tool results by tokens, bytes, repetition, log-to-useful-content proxy, and share of the next request. Recommend bounded output or isolation only from rule thresholds.
8. **P0: Model and effort counterfactual receipt.** Calculate actual cost by model and effort, then compute arithmetic deltas for cheaper models, lower effort, and bounded thinking. Correlate the counterfactual with observed test and merge outcomes, but never claim equivalent quality.
9. **P1: Batch, priority, Fast, and long-context calculator.** Select the exact provider price row, calculate Batch savings or Fast premium, record latency eligibility, and show the long-context delta. Use the actual table because providers publish distinct processing modes [20] [14].
10. **P1: Subscription/API break-even calculator.** Accept plan price, allowance, contracted rate, credits, and shared-pool rules as inputs. Compare observed API-equivalent cost with the entered plan and label the result a planning estimate, not an invoice [19].
11. **P1: Retry-storm and infinite-loop detector.** Detect repeated request, tool, parser, workflow, or state patterns, then calculate cost after first repetition and after each configured bound. Add hard-budget and timeout recommendations based on local policy [21] [21].
12. **P1: Edit-fail and no-progress detector.** Correlate edit acceptance, patch hashes, file state, tests, and time. Highlight cost after the first rejected or unchanged edit, using Claude Code's edit-decision fields where available [4].
13. **P1: Redundant-read and test-rerun detector.** Normalize command and state hashes to identify repeated file reads, unchanged full-suite reruns, and post-success verification. Show marginal cost and time, with a special alert for the measured high-verification pattern that cost 18.25x the clean-run median [25].
14. **P1: API-failure evidence detector.** Parse imports, compiler errors, undefined symbols, invalid parameters, 404s, and test failures. Use the neutral label `API-use failure evidence`; reserve `hallucinated API` for a proven local nonexistence check. This respects the benchmark-specific API-evolution rates [23] [23].
15. **P1: Final-claim consistency checker.** Compare final status language with tests, CI, Git diff, commit, and PR state. Emit a deterministic contradiction when the transcript says success after an objective failure, rather than asking a model to evaluate the prose [2] [26].
16. **P2: Cost per merged and surviving PR.** Join receipts to branches and PRs, report merged, unmerged, reverted, and abandoned denominators, and calculate cost per outcome. Include CI-failure counts because each additional failed check was associated with lower merge odds in the PR study [11].
17. **P2: Cost per accepted line and rework.** Use Git and line-count events to report raw additions, surviving additions, removals, reverts, and cost per surviving line. Mark LOC as a proxy and pair it with tests, review, and change-failure metrics [4].
18. **P2: Concentration, burn rate, and repository budgets.** Add top-user and top-repository shares, active-day and trailing-window burn, forecast bands based only on observed data, and versioned budget files. This implements FinOps showback and chargeback at the repository boundary [28].
19. **P2: CI cost and waste gates.** Provide a stable exit code for dollar, token, retry, test-rerun, long-context, or no-progress thresholds. Publish the receipt as a PR comment and an artifact so a gate is auditable.
20. **P2: OTel bridge and adapter capability matrix.** Import or export Claude Code OTel fields, preserve request and session correlation IDs, and state which cache, effort, tool, and cost fields each Claude Code, Codex, Cursor, Gemini CLI, and opencode adapter actually observed. Align the schema with existing dashboards that already surface cost, tokens, sessions, tools, latency, and errors [4] [15].
